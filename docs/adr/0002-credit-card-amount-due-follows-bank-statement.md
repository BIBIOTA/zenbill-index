# 信用卡應繳以銀行帳單為準，ZenBill 計算值只當預估與對帳訊號

信用卡「這次要繳多少」（應繳總額）原本完全由 ZenBill 從交易算出，而且有三種算法：總覽待繳用上期週期的淨消費；帳戶頁的繳卡費預設帶**目前檢視週期**的本期支出；自動扣款直接繳整個 `accounts.balance`。三者都對不上銀行帳單，原因有這些：沒有上期結轉和溢繳；ZenBill 以消費日（`occurred_at`）切期，銀行以入帳日切期；交易可能漏記或記錯。

我們決定新增**帳單**資料（`credit_card_statements`）。有帳單時，應繳總額以帳單為準（確定）；沒有時才用 `本期消費 + 結轉` 計算（預估）。兩者的差額顯示給使用者，當作對帳訊號。帳單由專案 skill 從 Gmail 電子帳單匯入，也可以在帳戶頁手動填寫。

## Considered Options

**只改善計算公式（否決）**：例如改用「結帳日當天的卡片餘額」當應繳。理論上這樣會自動包含結轉，但 `balance` 有歷史污染（例如手記的平帳調整），而且消費日和入帳日的落差無論公式怎麼改都還在。

**改用入帳日切期（否決，維持 2026-07-20 的決定）**：要在發票同步、手記、各種匯入的每一條寫入路徑都補上入帳日，成本高。有了帳單數字之後，這個落差只會影響預估，不會影響確定的數字。

**只用銀行數字（否決）**：帳單寄來之前、或沒有電子帳單的卡，就完全看不到應繳金額。

**混合（採用）**：帳單優先，預估當後援。預估的結轉只建立在前一期的**確定**帳單上，不往回遞迴，錯誤不會一路累積。

## Consequences

- 「應繳總額」與「本期消費」正式分成兩個詞（見 `CONTEXT.md`）。本期消費維持 TRANSFER 不計入的規則。
- 總覽、帳戶頁待繳區塊、繳卡費預設金額、自動扣款，都從後端同一處取得應繳總額。前端不再自己計算應繳。
- 自動扣款改繳「最近一期的應繳總額 − 已繳」，不再繳整個 `balance`。
- 帳單表不牽動 `balance`，所以 skill 直寫 DB 是安全的，不需要補餘額差額。
- `closing_day` 仍然是消費日的切點，帳單用 ZenBill 的 `cycle_end` 對應，不用銀行印的結帳日。
